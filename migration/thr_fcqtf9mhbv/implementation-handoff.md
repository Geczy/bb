## Behavior

Claude's root assistant authentication error survives the terminal result, including the recorded `subtype: success, is_error: true` shape. Only the two existing authentication codes are retained; the state clears across turn boundaries and on a subsequent non-auth assistant message. The existing `provider/error.errorInfo` persistence and daemon event transport carry it; no new recovery event or persistence format is needed. Previously stored untyped error prose is not reclassified from health or message text; a new explicit failed attempt supplies the structured category. Existing bridge session replacement and provider `--resume` behavior stay in place.

The failed error row offers Sign in and embeds the existing terminal component after a click. Cancel closes only that terminal. A zero exit says the command finished and asks the user to send a message; it does not claim an OAuth verification that did not happen. Completing, failing, or cancelling login never sends a turn, stops the provider, resets the thread, changes the draft, or edits workspace files.

The shared action is `sdk.terminals.create({ scope: { kind: "thread", threadId }, start: { mode: "provider-login", turnId }, cols: 80, rows: 24 })`. `turnId` is optional for callers asking to recover the current failure; the UI supplies the displayed failed turn. CLI: `bb terminal create --thread <id> --provider-login --attach`. The server rejects non-thread targets, stale/non-auth errors, active or successful turns, and retry-in-progress errors. It reads the login command on the execution host; health status does not gate eligibility and cannot trigger login. The regression specifically covers health reporting ready.

The daemon launches login directly as argv, without a login shell that could replace profile variables. It uses the retained thread execution environment, including custom `CLAUDE_CONFIG_DIR` and `BB_CLAUDE_CODE_EXECUTABLE`. It checks environment ID, provider ID, and the exact failed turn ID. No fallback to the primary host or default profile occurs. The runtime retains the most recently failed root turn ID and invalidates it when another turn starts; nested/stale completions cannot authorize login. Current provider/host environment resolvers are not rerun for the sign-in terminal.

These are supported failure outcomes, not silently defaulted sign-ins.
